# 实现闭环复核

先读取目标仓库生效的 `AGENTS.md` 及其指向的 AI 开发规范，按其中的通用要求判定；本 skill 只补充职责内的执行与验收。

## 闭环通过条件

下列条件用于功能实现。纯文档、提示词或 Skill 任务以事实准确、引用可用、执行决策符合任务边界和适用验证为准，不强造生产入口；只读复核交付发现与覆盖证据，不自动实施修复。

功能实现不是代码已经存在，而是同一需求项同时满足：

- 有真实生产入口和注册点，能够从 route、CLI、Worker、Scheduler、Collector 或运行时 registry 到达新实现。
- 主调用链已追到数据库、Redis、MQ、文件、外部服务或最终响应，成功、校验失败、下游失败、超时/取消和重试终态都有确定行为。
- 参数、权限/安全、事务、幂等、并发上限、资源释放、可观测性和恢复路径按真实故障模型处理；不适用项有源码依据。
- 受影响的契约、配置、Model/初始化 SQL、缓存、前端、文档、测试和运维步骤已记录修改文件或不适用依据。
- 受影响的项目自有 YAML 固定字段具有紧邻且同缩进的中文注释，字段用途、取值/空值、生效方式和安全约束与配置源码一致；动态 map 与第三方 schema 的共享说明或排除依据已记录。
- 按公共规范复核新增、修改及受影响的原有注释是否真实、属于当前位置职责，并准确反映状态、副作用和失败结果；同时沿方法/函数和完整功能业务块核对核心规则、多步骤、状态流转、复杂判断、异常边界、非直观实现和并发一致性解释是否充分，缺少必要说明不得判定完成。简单操作不机械翻译，多项约束可用多行，不以注释数量或篇幅验收。
- 最后一次修改后的适用验证已通过；无法执行的检查明确标记未验证，不能把替代性静态检查写成生产验证。
- 交付状态与事实一致：待 DBA 执行 SQL、待发布、待清缓存或待重启属于“交付待人工执行”，不是“已上线”。

## 工作流程

1. 根据最新用户要求、历史约束和修改前检查过的源码证据，还原用户真实需求。
2. 确认最终实现仍匹配已确认意图；如果意图含糊且未确认，不要称为完成，要标记风险。
3. 交付前为每个可独立验收的需求项建立复核记录：源码或规则消费入口、修改文件、被触发的同步面、验证证据和剩余风险。
4. 功能实现端到端追真实调用链。生产入口未接上时，不能只凭 helper、DTO、UI 壳或孤立测试声称完成；纯规范、提示词或 Skill 任务按上述事实、引用、执行决策及适用验证判定。
5. 生产入口未接上不自动等于代码无用。先判断它是否为稳定扩展契约、已有多实现入口、外部依赖隔离、跨服务共享约定、CLI/Make/测试/运维能力；满足任一项且职责、测试和接入边界明确时，记录为“基础能力/未激活”，既不删除也不计入生产闭环。
6. 涉及 HTTP 协议的功能建立入口矩阵时，覆盖 route → middleware → handler/worker → response/output，单独列出 download、Range、SSE、长轮询、批量和大响应；普通 JSON 测试全绿不能替代这些协议边界。
7. 检查当前仓库真实存在且受影响的交付面：handler/API、logic/service、model/repository、config/YAML、SQL/Lua、Redis Key、文档、前端 wrapper/type/i18n、权限/业务码、测试和运维说明。配置面逐字段核对 config struct/tag、默认值、normalize/getter、校验器、消费方、reload/restart 与 YAML 同缩进行级注释，不能以父节点概述或 YAML 可解析代替；不存在的面标记不适用；SQL 变更必须证明 GORM 链式优先或原生 SQL 例外及性能保护。
8. 涉及 DDL/DML 时，确认仓库只更新完整初始化基线、没有新增日常迁移版本或碎片化 SQL；存量库本地 SQL 被忽略且已形成 DBA/运维执行、验证和恢复闭环。
9. 代码变更后复核命名和结构：目录、文件、变量、函数、方法、常量、结构体、接口和字段必须匹配业务职责；新增接口必须存在外部依赖、真实替换点、依赖环或多个实现，新增 helper 必须收口稳定重复规则或显著缩短主流程，只转发参数且无独立职责的 wrapper 应内联。
10. 拒绝半成品收口：脚手架、样例、单一分支、happy path 或未验证接线不能描述为完成；无法完成时明确未完成项、阻塞、影响和下一步。补测试应在同一业务源码对应的一个测试文件内扩展，不能因函数、场景、fixture 或单元/集成而分拆；构建/包约束冲突报告依据，既有布局调整须有明确授权。
11. 验证证据必须来自最后一次修改后的同一候选快照；worktree 与 index 不一致时，不能混用两者结果声称闭环。
12. 最终说明要诚实区分：已完成、已验证、已交付待执行、已跳过、被阻塞和需后续处理。
13. 问题与阻塞按“正常逻辑缺陷”“极端运行条件”“验证环境阻塞”分栏。极端运行条件内再判定代码已在超时内返回受控错误且释放资源，还是存在无界阻塞/重试、误写数据、资源泄漏、伪成功、进程退出等韧性缺陷。每栏分别写触发条件、证据、期望/实际行为、影响、代码责任和处理结论，不得混合列举或合并计数。

纯规范、提示词或 Skill 更新只验证事实、引用及规则决策；不得把文案更新表述为已完成源码注释审计、代码质量整改或测试文件整合。

## 命名规则

- 优先使用短而准确的领域名，避免长解释型命名。
- 避免 `handleData`、`doProcess`、`DefaultValue`、`CommonConfig`、`Manager`、`Helper`、`Info` 等泛名，除非本地代码已赋予明确含义。
- 实现职责变化时同步改名，不保留描述旧行为的名字。
- 常量按领域前缀和稳定业务含义分组。
- 结构体用于领域对象；符合仓库风格时，请求用 `Req`、响应用 `Resp`、列表项用 `Item`。
- 只有真实替换点才抽接口，不为了显得抽象而新增接口。
- 目录和 package 名要匹配归属，不创建装杂物的 catch-all 目录。
- 新增抽象、目录、框架或依赖前，必须确认成熟方案、必要性、替代方案、维护成本和开发确认结果。

## 闭环复核记录

以下字段是每个需求项都需要的完成证据，因此保持固定；`同步面` 的内部内容按源码影响动态展开，不要求为仓库不存在或未触发的技术面制造空字段。非平凡任务内部使用这个结构，并在最终交付中摘要：

```text
需求项:
确认意图/依据:
入口/调用链:
实现文件:
同步面:
验证:
诊断分类: normal-logic | extreme-condition | validation-environment
状态: completed-and-verified | completed-unverified | handoff-pending | skipped | blocked
说明:
```

`同步面` 先从代码、API/业务码/权限/安全、配置、Model/初始化 DDL/DML、SQL/Lua、Redis、前端、文档、测试和运维步骤中识别实际触发项，再逐项记录源码依据与修改文件；只有常见风险面可能被误判时才写不适用及具体证据。`验证` 必须写命令、目录、范围、结果和候选快照。禁止填写“相关内容已同步”“测试正常”。
