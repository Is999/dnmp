# Go AI 实现防漂移

先读取目标仓库生效的 `AGENTS.md` 及其指向的 AI 开发规范，按其中的通用要求判定；本 skill 只补充职责内的执行与验收。

## 禁止用术语代替检查

- 说“闭环”时，必须列出生产入口、主调用链、成功与失败分支、最终副作用、注册/配置、同步面和验证；只有 helper、脚手架、DTO、单一分支或孤立测试时判定为未闭环。
- 说“简洁、清晰、可维护”时，必须逐个检查新增目录、接口、结构体、状态、分支、wrapper 和 helper 的当前调用方与职责；没有需求、调用方、稳定复用边界或故障证据的层级不得保留。
- 说“已同步”时，必须先从 route、request/response、RouteMeta、权限/安全、业务码/i18n、配置、Model、初始化 DDL/DML、SQL/Lua、Redis Key、前端契约、文档、测试和运维步骤中识别源码触发面，再记录每个触发面的依据、修改文件和验证结果；不得用汇总“不适用”代替未执行检查。
- 说“验证通过”时，必须给出最后一次修改后的命令、执行目录、范围和结果；旧快照、只测 helper、只编译或只跑 happy path 不算当前候选版本的完成证据。

## 新增实现与已有代码的注释

- Go 方法实现或修复前使用 `$go-comment-style-audit`；其它语言执行公共规范“注释要求”，不运行不适配的 Go 审计器。首次代码补丁带必要说明，简单操作不机械翻译，方法/函数职责及完整功能业务块须说明，核心规则、多步骤、状态流转、复杂判断、异常边界、非直观实现和并发一致性在生效处解释充分，可用多行。
- 变更职责、条件、状态、副作用或失败/并发行为时同步核对受影响的旧注释及调用处，失效内容重写或删除；不得保留新旧矛盾说明、开发历史和未来计划。
- 仅补注释先核实实现、契约和测试，不夹带业务改动；缺口在代码之外报告。交付前同时查误导/冗余注释和复杂逻辑解释不足，不以注释数量或绿色测试替代。

## 工作流程

1. 先确认准确仓库，读取生效的 `AGENTS.md` 链路，并用 `rg --files` 发现当前仓库实际存在的 AI 开发文档。
2. 需求含糊、只要求分析、存在两个以上会改变实现文件或外部行为的合理解释，或将改变 API、数据、权限、安全、缓存兼容、迁移/补偿和用户可见流程时，先使用 `$requirement-intent-gate`，不要猜业务意图。
3. 修改前先读现有代码路径：目录结构、代码风格、调用链、数据契约和测试。
4. 非平凡任务要先说明实现边界：目标行为、源码依据、可能修改文件、明确非目标和已确认假设。
5. 闭合完整生产路径，而不是只写 helper 或脚手架；多分支、多入口、多同步面需求交付前使用 `$implementation-closure-review`。
6. 改动保持小而聚焦；优先复用现有 helper、包、错误包装、logger、配置模式、SQL/Lua 资产加载器和测试风格。遇到成熟通用能力、高风险基础设施或手写实现容易出错的场景，先检查成熟依赖/框架；确需新增抽象、目录、依赖或框架时，先说明必要性、替代方案、影响范围和验证方式，并让开发确认。新增回归先定位业务源码对应的已有 `_test.go`，按公共规范“测试文件组织”扩展；不按函数、场景或单元/集成派生文件，不以规范更新授权调整旧测试布局。
7. 按下方“实现判定清单”逐项复核结构和抽象；禁止只写“代码简洁、逻辑清晰”后跳过 wrapper、接口、状态与故障边界检查。
8. 按下方命名标准逐项复核目录、文件、变量、方法、常量、结构体、接口和字段；职责变化时同步改名，不能只判断名称长短。
9. 按下方注释标准检查新增、修改及受影响的原有说明，同时检查复杂流程解释不足；不以标识符未导出、脚本零告警或注释数量代替内容核对。
10. 最后一次修改后先运行每个改动文件的归属包测试；共享类型、helper、RouteSpec、配置、Model 或注册清单变化时，再运行全部直接调用包和 `go test ./...`。全量命令被数据库、Redis、外部服务或工具链阻塞时，记录原命令、第一处错误、未覆盖包，并运行全部可执行的归属包与直接调用包测试。
11. 交付前在每个触碰的 Git 仓库运行 `git diff --check` 和 `git status --short`；只把本轮新增交付文件加入索引。

## 故障分类与输出

- 正常逻辑缺陷：依赖健康、配置有效且普通业务输入或已声明并发范围可触发错误结果/状态，例如判断式把 `1 > 2` 返回为 `true`。必须修正代码并补稳定回归测试。
- 极端运行条件：生产事件或主动故障注入已经执行到 Redis、MySQL、MQ、DNS、网络、磁盘或资源不可用的错误处理代码时，先记录外部触发条件，再标记“代码处理符合预期”或“存在韧性缺陷”。在明确超时内返回受控错误、不误写数据且正确释放资源时，不记为代码 bug；出现无界阻塞/重试、误写/误删数据、资源泄漏、伪成功或终止进程时，记为韧性缺陷。
- 验证环境阻塞：验证原本要求依赖健康，但本地缺少 Redis、MySQL、Docker、专用校验器或权限并在到达待测代码前失败，只说明验证路径未覆盖，不能单独证明生产代码有 bug，也不能写成已验证。相同的 `connection refused` 必须按验证目标和实际到达的代码边界分类，不能只按错误文本判断。
- 分析和交付时按“正常逻辑缺陷”“极端运行条件”“验证环境阻塞”三栏输出，每项写明触发条件、源码/日志/测试证据、期望与实际行为、影响范围、是否修改代码和后续责任；禁止混合排序或合并统计。

## 必读资料

目标仓库、仓库内 AI 文档或验证命令不清楚时，读取 `references/project-map.md`。

## 实现判定清单

### 入口与调用链

- 从 route、CLI、Worker、Scheduler、Collector、bootstrap spec 或运行时 registry 中确认真实入口，并追到 handler/consumer、logic/jobs、model/infra 和 response/output。新文件没有注册或调用方时判定为孤立实现。
- 对每个需求分支列出输入条件、状态变化、数据库/Redis/MQ/文件/外部服务副作用和最终输出；成功、校验失败、下游失败、超时/取消与重试终态均应有确定行为。
- 修改启动期组件时核对注册、配置、默认值、关闭顺序和重启边界；修改运行期参数时核对 normalize/getter、reload 应用器、回退行为和可观测状态。

### 结构与抽象

- 基础实现不得反向导入具体业务包或硬编码业务表/字段、状态、规则和站点特例；业务只能经已有基础能力、稳定契约及注册/注入点接入，装配留在业务入口或组合根。复核静态引用和动态装配是否绑定具体业务；基础经稳定契约执行业务注入实现属于既有扩展接入，不算反向依赖，但不得识别具体业务类型或规则。不以 `common/helper` 命名或回调包装证明通用；边界不清时报告文件、符号、调用链与最小分离方案，不擅改核心或预建新层。
- 只转发参数且不承担校验、转换、事务、重试、缓存、指标或外部依赖隔离的 wrapper 应内联；连续 wrapper/helper 跳转不能隐藏真实业务分支或副作用。
- 新增接口必须满足至少一项：已有两个及以上实现、隔离外部依赖或解除真实依赖环；仅为 mock 一个纯业务具体类型不构成准入理由。
- 新增 helper 必须收口已经稳定的重复规则，或明显缩短主流程；单调用方但职责明确的完整业务块可合理拆分，只有一行转发、没有独立职责或名字比逻辑更难理解时不提取，不以调用次数衡量质量。
- 锁、租约、事务、CAS、幂等、超时、取消、重试和状态机如果保护可复现的并发或故障窗口，属于正确性边界；不得为了减少代码行数删除。

### 命名与注释

- 名称必须对应当前业务对象或动作；`handleData`、`doProcess`、`CommonConfig`、`DefaultValue`、无领域限定的 `Manager/Helper/Info` 视为待复核泛名。
- 按公共规范核对声明、稳定契约和关键逻辑的真实语义；未导出不豁免业务边界，直观操作不逐行翻译。方法/函数职责、完整功能业务块及核心规则、多步骤、状态流转、复杂判断、异常边界、非直观实现、并发一致性就近说明充分，可用多行；行为变化同步核对旧注释及调用处，不用说明掩盖实现缺口。
- 项目自有 YAML 固定字段必须有紧邻上方、同缩进的中文注释，父节点不能替代子字段。
- YAML 字段注释必须说明消费组件和用途；源码定义了枚举/范围/单位、缺省/空值/零值、normalize/getter、reload/restart、敏感信息或跨字段约束时逐项写明。动态 map 重复项只有在父字段已经定义 key/value、空值和合并语义时可不重复；第三方 schema、纯数据清单或生成文件必须记录路径、schema 所有者和排除依据。

### 改动范围与兼容

- 每个修改文件和关键 diff 必须映射到需求项、必要同步面或验证修复；无映射的重命名、格式化、目录移动和顺手重构移出本任务。
- 默认保持请求/响应字段、业务码、权限、安全策略、配置键、数据库/Redis 数据形状、错误、事务、时序和外部副作用；改变时列出当前行为、目标行为、调用方和发布/回退步骤。遵守目标仓库的基线策略，只有已确认存在跨版本部署要求时才讨论兼容窗口，禁止为唯一基线项目新增历史兼容分支。
- 不回滚用户已有改动，不用大范围重构掩盖局部问题。没有生产入口只能证明未启用；样例、兼容分支或未来占位只有经三分类确认不承载扩展契约、共享约定、测试、部署或运维能力后才可删除。

## 后端硬规则

- 运行期可由请求、消息、任务、热更新、外部依赖、重复注册、超时或取消触发的失败必须返回 `error`、业务码或受控任务失败；禁止在服务运行路径使用 `panic`、会 panic 的 `Must*`、`log.Fatal*`、logger `Panic*`、`os.Exit`、`syscall.Exit` 或 `runtime.Goexit`，也禁止用 Recover 代替输入校验和错误传播。路由、组件、指标等注册必须在 `App.Start` 前完成，逐层返回到 bootstrap 并在失败时清理已创建资源；只有 `cmd/*` 主入口可在服务尚未监听，或全部监听器和后台组件已经停止且资源清理完成后，把最终进程结果转换为退出码，失败结果必须非零。只有包初始化读取编译期固定常量或 `go:embed` 资产、触发条件不受运行期输入影响且有完整性测试时，才允许用 `panic` 表示构建资产损坏，并写明不可恢复依据。
- 仓库规范要求时，使用 `github.com/Is999/go-utils/errors` 包装错误。
- `error` 级日志只放在 handler、worker、scheduler、startup、health 等外层；内层逻辑返回包装后的错误。
- MySQL/SQL 默认使用 GORM 链式调用；只有 GORM 无法安全表达或会明显影响性能时才使用原生 SQL。
- 接受原生 SQL 时，必须记录原因、索引依据、预估扫描范围、分页或批量上限、超时、并发和 DB 压力控制。
- 随应用运行的原生 SQL 放在 `*.sql.tmpl`，Redis Lua 放在 `.lua`，并通过 `go:embed` 加载。
- DDL/DML 变更直接更新完整初始化基线，不新增碎片化迁移 SQL 或日常迁移版本；存量库本地 SQL 放在被忽略的 `data/sql-changes/<change-id>/`，只交付 DBA/运维执行。
- 执行 SQL/Lua 前，使用 `embedasset.StripLeadingLineComments` 或本包 helper 剥离文件头说明。
- 新增或修改 SQL 路径前，评估执行计划、索引、基数、返回行数、batch、cursor、timeout、concurrency 和库压力。
- 包装 `http.ResponseWriter` 时，必须核对 `Flusher`、`Hijacker`、`Pusher`、`ReaderFrom`、`Unwrap`、Range、取消和真实写错误语义；无改写需求时直接透传，禁止把下载或大响应无上限整包缓存。
- 除非用户明确要求，保持外部 YAML、API、权限、业务码、前端类型和文档契约稳定。
- 不要把脚手架、样例逻辑、happy path 或多分支需求中的单一分支称为完成。

## 交付检查

- 每个需求项对应的入口、调用链、实现文件和最终副作用。
- 正常逻辑缺陷、极端运行条件和验证环境阻塞的分栏结论；极端运行条件标明代码处理符合预期或存在韧性缺陷，没有某栏时写明“未发现”。
- 每个源码触发面的依据、修改文件与验证结果；常见风险面若判定不适用，附具体证据；同时列出明确非目标。
- 最后一次修改后的验证命令、执行目录、结果和未覆盖路径。
- 当前状态属于已完成且已验证、已完成但未验证、已跳过、被阻塞还是交付待人工执行。
- 是否需要新库初始化、DBA/运维 SQL、回填、缓存失效、配置 reload、进程重启、回滚或补偿。
